# خطة التنفيذ التفصيلية لتطوير منصة Lms Upgrade

**الإصدار:** 1.0  
**النطاق:** تطوير قلب المنصة فقط، مع الإبقاء على النظام الحالي عاملًا وعدم كسر عمليات الشراء أو صلاحيات الطلاب الحالية.  
**المنتج المستهدف:** منصة تعليمية مدفوعة لطلاب الثانوية، تجمع بين المحتوى المرئي، التقييم، التقدم، المبيعات، وإدارة الطلاب.  
**المرجع الفني:** مستودع [`sayouuuuud/lms`](https://github.com/sayouuuuud/lms)، مع مطابقة النسخة المنشورة للـ commit `73052713d2dea8fb08793099785729221ae49ce2`.  
**طريقة التنفيذ المقترحة:** مراحل متتابعة، وكل مرحلة تنتهي بمعايير قبول واضحة، وتمر على staging قبل الوصول إلى قاعدة `upgrade` الإنتاجية.

> **المبدأ الأساسي:** لا نضيف صفحات منفصلة لمجرد زيادة عدد الصفحات؛ بل نبني خدمات ومصادر حقيقة مشتركة تجعل الصلاحيات، المحتوى، التقييم، التقدم، الدفع، والتحليلات تعمل فوق نفس نموذج البيانات.

## 1. النتيجة المستهدفة

الهدف النهائي هو نقل المنصة من نموذج «الطالب يشتري ويشاهد فيديو» إلى نموذج «الطالب لديه مسار تعليمي قابل للقياس». المسار المستهدف هو:

> اختيار المرحلة والفرع → اختيار المنتج أو الاشتراك → فتح المحتوى المسموح → اتباع خطة تعلم → مشاهدة الدرس → اجتياز اختبار قصير أو واجب → تحديث خريطة الإتقان → مراجعة موجهة قبل الامتحان → تدخل إداري أو تعليمي عند التوقف.

في المقابل، يحصل المدرس والإدارة على استوديو لإنتاج المحتوى، نظام Release، فحص جودة قبل النشر، صورة كاملة لكل طالب، مركز تشغيل للفيديو والطلبات، تحليلات تعليمية، وقرارات قابلة للتنفيذ بدل تقارير رقمية منفصلة.

## 2. قيود لا يجوز كسرها

| القيد | قاعدة التنفيذ |
|---|---|
| استمرار النظام الحالي | الطلبات الحالية، صلاحيات المحاضرات، روابط الفيديو، والطلاب الموجودون يجب أن تستمر دون إعادة شراء أو إعادة إنشاء سجلات. |
| الاشتراكات اختيارية | النظام الحالي one-time purchase يظل مدعومًا. يضاف الاشتراك أو الـ Bundle على مستوى المدرس/المحتوى/المنتج عبر وضع بيع واضح: `one_time` أو `subscription` أو `both`. |
| حماية قاعدة الإنتاج | لا migration مباشرة على `upgrade` قبل backup قابل للاسترجاع وتجربة على staging نسخة من المخطط والبيانات اللازمة. |
| الصلاحيات | كل Feature جديدة تمر من Entitlement Service، وتُراجع مع `auth-guard` وRLS؛ لا نكرر شروط الوصول داخل كل صفحة. |
| المحتوى المنشور | لا يظهر محتوى غير مكتمل للطالب. كل نشر يمر عبر Content QA وحالة Release. |
| الخصوصية | Student 360 لا يعرض إلا ما يحتاجه الموظف حسب صلاحياته، مع إخفاء الأسرار وبيانات الدفع الحساسة وتسجيل الوصول للبيانات الحساسة. |
| الفيديو | أي retry أو تغيير حالة يجب أن يكون idempotent، ولا ينشئ jobs مكررة أو صلاحيات مشاهدة زائفة. |

## 3. خط الأساس الذي نبني عليه

المشروع الحالي يضم Next.js/React وPrisma وPostgreSQL، مع مسارات إدارية وطلابية، Auth.js/NextAuth، RLS، محتوى فيديو HLS/R2، طلبات ومدفوعات، امتحانات، تقدم، أجهزة وجلسات، وWhatsApp. قاعدة `upgrade` تحتوي على بنية أعمال فعلية تشمل الطلاب والمحتوى والطلبات والفيديو والامتحانات.[1]

يوجد خطر تشغيلي سابق يجب أن يكون **أول بند في التنفيذ**: النسخة المنشورة تشير إلى مورد PostgreSQL لا يحتوي قاعدة `upgrade`، بينما قاعدة `upgrade` الصحيحة موجودة في مورد آخر. كما أن التطبيق يعمل داخليًا لكن بعض المسارات التي تعتمد على Prisma تفشل. لا ينبغي بناء Features فوق هذا الخلل.[2]

## 4. الخطة العامة ومراحل التنفيذ

التقدير التالي مبني على فريق صغير يضم مطور Full-stack، ومطور Backend/Database جزئيًا، ومراجعة Product/QA. إذا كان التنفيذ بمطور واحد فقط، فالأفضل مضاعفة المدة وعدم تنفيذ المراحل المتوازية في قاعدة الإنتاج.

# المرحلة 0: تثبيت خط الأساس وإصلاح الإنتاج

## الهدف

جعل النسخة الحالية قابلة للاستخدام والمراقبة قبل إضافة أي سلوك جديد. هذه ليست مرحلة تجميل؛ هي شرط حتى لا تختلط أخطاء البنية التحتية بأخطاء Features جديدة.

## الأعمال

أولًا، تصحيح `DATABASE_URL` و`DIRECT_URL` في مورد التطبيق ليشيرا إلى مورد PostgreSQL الذي يحتوي قاعدة `upgrade`، مع اختبار Prisma connection وAuth وقراءة catalog من داخل التطبيق. ثانيًا، ضبط hostname والـ proxy والـ HTTPS والتأكد من أن الرابط الخارجي يصل إلى الحاوية الصحيحة. ثالثًا، تحديد مكان تشغيل transcoder: إما إضافة worker رسمي للنشر، أو توثيق أنه يعمل في خدمة خارجية مع health check وheartbeat واضح.

بعد ذلك نضيف health checks للتطبيق وقاعدة البيانات وR2 وWhatsApp وvideo worker، ونوحّد logs بصيغة تحتوي `request_id` و`user_id` المموه و`entity_id` و`action` و`duration_ms` دون أسرار. نجهز staging منفصلة ونسخة backup قابلة للاسترجاع قبل أي migration.

## مخرجات القبول

| الاختبار | معيار النجاح |
|---|---|
| تسجيل الدخول | نجاح login وregister وverify من خلال proxy الخارجي. |
| Prisma | لا يظهر `Database upgrade does not exist` في logs. |
| الفيديو | رفع/معالجة/تقديم فيديو تجريبي من البداية للنهاية. |
| الاسترجاع | استعادة backup إلى staging وقراءة الجداول الرئيسية. |
| المراقبة | تنبيه عند توقف التطبيق أو فشل worker أو تراكم jobs. |

# المرحلة 1: تصميم نموذج المجال والصلاحيات الموحد

## الهدف

تحديد لغة موحدة للمنتجات والمحتوى والصلاحيات والتقدم قبل بناء الواجهات. أهم قرار هنا هو فصل **المنتج الذي يُباع** عن **المحتوى الذي يُفتح** وعن **السبب الذي منح الصلاحية**.

## نموذج الصلاحية المقترح

نضيف مفهومًا منطقيًا باسم `Entitlement`، ومعناه أن طالبًا معينًا يملك حق الوصول إلى مورد معين خلال فترة محددة.

| الحقل المنطقي | الغرض |
|---|---|
| `student_id` | صاحب الصلاحية. |
| `resource_type` | lecture، course، term، bundle، subscription، lesson أو exam. |
| `resource_id` | المورد المفتوح. |
| `source_type` | order، subscription، coupon، manual_grant، admin، scholarship. |
| `source_id` | الطلب أو الاشتراك أو المنحة التي سببت الصلاحية. |
| `starts_at` / `expires_at` | بداية ونهاية الصلاحية. |
| `status` | active، expired، revoked، pending. |
| `metadata` | تفاصيل غير حرجة، مثل سبب المنح أو campaign. |

لا يتم حذف الصلاحيات القديمة عند الإلغاء؛ تتحول إلى `revoked` مع سبب وسجل تدقيق. هذا مهم للدعم والمحاسبة.

## مخرجات القبول

يتم اعتماد قاموس domain موحد، ومخطط صلاحيات، ومصفوفة role/action/resource، مع اختبارات مكتوبة للحالات: شراء محاضرة، شراء كورس، شراء ترم، اشتراك منتهي، كوبون، منحة إدارية، ومستخدم admin.

# المرحلة 2: Entitlement Service ونظام الطلبات والدفع

## الهدف

إضافة نظام مرن للصلاحيات والمنتجات دون كسر النظام الحالي. يجب أن يصبح القرار «هل يحق لهذا الطالب فتح هذا الدرس؟» صادرًا من خدمة واحدة، حتى تستخدمه صفحة الطالب وAPI الفيديو وprogress actions والامتحانات.

## دعم النظام الحالي والاشتراكات الاختيارية

نضيف إلى المنتج أو محتوى المدرس إعدادًا مثل:

```text
sales_mode = one_time | subscription | both
```

ويُسمح للمدرس باختيار طريقة البيع لكل منتج أو مجموعة محتوى. في وضع `one_time` لا يظهر الاشتراك. في وضع `subscription` لا يظهر الشراء الفردي. في وضع `both` تظهر الطريقتان، ويُسجل لكل عملية مصدر الصلاحية. لا نغير الطلبات القديمة ولا نحولها إلى اشتراكات.

الاشتراك يجب أن يكون كيانًا مستقلًا، مثل `subscriptions` و`subscription_plans` و`subscription_events`. الـ Bundle يجب أن يكون تجميعًا لموارد محددة، مثل كورسات أو محاضرات، مع صلاحية ناتجة عنه في Entitlement Service. لا نربط الوصول مباشرة بشرط مبعثر في الواجهة.

## Order State Machine

الحالات المقترحة هي `pending` ثم واحدة من `approved` أو `rejected` أو `expired` أو `cancelled`. كل انتقال يسجل في `order_events` مع الفاعل والسبب والوقت. عملية approval يجب أن تكون idempotent عبر transaction وunique idempotency key، حتى لا تتكرر الصلاحية أو رسالة WhatsApp عند الضغط مرتين.

## مخرجات القبول

يستطيع النظام معرفة سبب صلاحية أي طالب في أقل من استدعاء منظم، وتظهر صفحة الطلب timeline واضحًا، ولا يتكرر منح الصلاحية أو إرسال إشعار عند تكرار نفس العملية. تعمل المنتجات الحالية كما كانت، ويمكن اختبار منتج جديد بوضع اشتراك دون التأثير على النظام القديم.

# المرحلة 3: Student 360 والدعم وإدارة الأجهزة

## الهدف

إنشاء شاشة تشغيلية واحدة للإدارة تختصر رحلة البحث بين عدة صفحات.

## مكونات Student 360

تحتوي الشاشة على ملخص الهوية والدور، حالة الطالب، المرحلة والفرع، المنتجات والصلاحيات مع سبب كل صلاحية، الطلبات وسجل حالاتها، التقدم والمشاهدة، الامتحانات والنتائج، الأجهزة والجلسات، الرسائل والإشعارات، ومؤشرات الخطر. كل قسم يملك صلاحية عرض منفصلة حسب دور الموظف.

نضيف مركز Support Inbox بتذاكر لها تصنيف وأولوية وحالة وموظف مسؤول، مع ربط التذكرة بالطالب والطلب والدرس والجهاز. لا ننسخ بيانات الطالب داخل كل تذكرة؛ نستخدم references حتى تظل البيانات محدثة.

في إدارة الأجهزة نعرض سبب المنع والـ risk signals والـ last seen، ونوفر actions مثل revoke session وremove device وtrust device، وكل إجراء يحتاج سببًا ويسجل في audit log.

## مخرجات القبول

يستطيع موظف الدعم حل مشكلة «لا أستطيع مشاهدة الدرس» من شاشة واحدة، مع معرفة هل السبب شراء أم اشتراك أم جهاز أم فيديو أم قاعدة بيانات. ولا يستطيع الموظف رؤية المدفوعات أو الرسائل إلا إذا كان دوره يسمح بذلك.

# المرحلة 4: Content Studio وContent QA

## الهدف

تحويل صناعة المحتوى من إدخال سجلات منفصلة إلى Workflow واضح للمدرس أو محرر المحتوى.

## Content Studio

يُبنى المحتوى كحزمة مترابطة:

> هدف الدرس → محاضرة → درس/فيديو → ملخص ومرفقات → أسئلة قصيرة → واجب أو امتحان → Release.

يدعم الاستوديو Draft، Preview as Student، حفظ Version، إضافة ملاحظات داخلية، ترتيب الدروس، تحديد prerequisite، ربط المهارة أو الموضوع، وإرسال المحتوى للمراجعة. يمكن للمحرر رؤية ما ينقص قبل طلب النشر.

لا نسمح بتعديل النسخة المنشورة بطريقة تكسر سجل الطلاب؛ كل تغيير جوهري ينشئ version جديدة، بينما تظل version القديمة مرئية للتدقيق.

## Content QA

الفحص الآلي يبحث عن الدروس بلا فيديو، الفيديوهات بلا درس، المحاضرات بلا كورس، روابط HLS غير صالحة، صور أو مرفقات مفقودة، أسعار غير منطقية، امتحانات بلا أسئلة، أسئلة بلا إجابات، محتوى منشور بلا targeting، وprerequisites دائرية.

## مخرجات القبول

لا يمكن نشر عنصر يفشل في checks حرجة. أما التحذيرات غير الحرجة فيمكن تجاوزها فقط بصلاحية مناسبة مع تسجيل السبب. يحصل المدرس على Preview مطابق لما سيراه الطالب بعد النشر.

# المرحلة 5: نظام Release وجدولة المحتوى

## الهدف

إدارة ظهور المحتوى للطلاب بشكل آمن ومرن، بدل أن يكون ظهور المحتوى نتيجة مباشرة لحفظ السجل.

## حالات Release

نستخدم حالات `draft` و`in_review` و`approved` و`scheduled` و`published` و`unpublished` و`archived`. لكل Release وقت نشر اختياري، ووقت إلغاء اختياري، ونطاق طلاب أو مرحلة أو فرع إذا كان ذلك مطلوبًا.

يدعم النظام النشر الفوري، النشر المجدول، فتح درس بعد مدة من الاشتراك، وفتح درس بعد إكمال prerequisite. يجب أن يتم حساب availability في Entitlement/Content Access layer، لا في الواجهة فقط.

## مخرجات القبول

يمكن تجهيز كورس شهر كامل مسبقًا، اختباره كطالب، جدولة دروسه، ثم إيقاف Release واحد دون حذف البيانات أو التأثير على progress القديم. كل نشر له actor ووقت ونسخة وملاحظات.

# المرحلة 6: إعادة بناء الامتحانات والواجبات

## الهدف

الانتقال من submission بسيط إلى نظام تقييم قابل للتدقيق والتحليل.

## نموذج الامتحان

نضيف `exam_attempts` مستقلة عن `exam_submissions`، بحيث يحمل كل attempt الطالب والامتحان والإصدار والبدء والانتهاء والمدة والحالة والدرجة. نضيف autosave للإجابات، timer server-side، منع التكرار غير المقصود، randomization اختياري، question snapshot حتى لا تتغير إجابة الطالب إذا عدّل المدرس السؤال بعد بدء المحاولة، وحالات واضحة مثل `in_progress` و`submitted` و`graded` و`expired`.

الأسئلة الموضوعية تصحح آليًا، والأسئلة المقالية أو الملفات تدخل manual review. كل تغيير في الدرجة يسجل في grade events. يجب جعل stage/branch targeting واضحًا ومتحققًا منه عند إنشاء الامتحان، مع تحذير صريح إذا كان الامتحان عامًا.

## مخرجات القبول

يمكن للطالب استكمال محاولة بعد انقطاع الشبكة، ولا يستطيع تمديد الوقت بتغيير ساعة الجهاز، ولا تتغير نتيجة محاولة قديمة بسبب تعديل السؤال. يستطيع المدرس مراجعة الإجابات وتعديل درجة مع سبب، وتستطيع الإدارة استخراج أداء حسب امتحان وفرع وموضوع.

# المرحلة 7: خريطة الإتقان ومراجعة ليلة الامتحان

## الهدف

ربط المحتوى والأسئلة والنتائج بمهارات أو Topics، وتحويل الدرجات إلى توصيات تعليمية.

## خريطة الإتقان

نضيف كيانات مثل `skills` أو `topics`، ونربط بها الدروس والأسئلة والامتحانات. يحسب النظام mastery score لكل طالب وموضوع من مزيج حديث من: نتيجة الأسئلة، تكرار الخطأ، حداثة المحاولة، وإكمال المحتوى. لا نعرض رقمًا زائفًا بدقة عالية؛ نستخدم مستويات واضحة مثل لم يبدأ، يحتاج مراجعة، متوسط، متقن.

كل تحديث يجب أن يكون قابلاً للتفسير: «المستوى منخفض لأن الطالب أخطأ في 4 من 6 أسئلة مرتبطة بالموضوع». لا نبدأ بنموذج AI معقد؛ نبدأ بقواعد deterministic قابلة للاختبار ثم نطورها.

## مراجعة ليلة الامتحان

يحدد الطالب الامتحان وموعده والوقت المتاح يوميًا. النظام ينشئ خطة مراجعة تشمل الدروس الضعيفة، الأسئلة السابقة، ملخصات، واختبار محاكاة. إذا لم ينفذ الطالب يومًا، تعاد جدولة الخطة بدون فقدان التاريخ.

## مخرجات القبول

يستطيع الطالب معرفة نقاط ضعفه، وتستطيع الإدارة رؤية أكثر المهارات ضعفًا على مستوى الفصل أو الفرع. كل توصية تربط بمحتوى أو سؤال موجود، ولا تظهر توصية بلا سبب مفهوم.

# المرحلة 8: تجربة التعلم والإنقاذ والشارات

## الهدف

توفير رحلة يومية واضحة وزيادة الاستمرارية دون تحويل المنصة إلى لعبة مزعجة.

## تجربة التعلم

يصبح Dashboard الطالب مبنيًا على Next Best Action: أكمل من حيث توقفت، شاهد الدرس التالي، راجع خطأً متكررًا، نفذ هدف الأسبوع، أو ابدأ محاكاة. كل بطاقة تقود إلى إجراء واحد، وتظهر نسبة إكمال الكورس وسجل آخر مشاهدة والدروس المتأخرة.

## نظام إنقاذ الطلاب المتوقفين

تعرف المنصة حالات مثل: اشترى ولم يبدأ، بدأ وتوقف، فشل في موضوع متكرر، أو انقطع قبل امتحان. ينشئ النظام قائمة rescue للإدارة مع سبب التوقف المقترح وإجراء مناسب: رسالة WhatsApp، خطة عودة، تمديد صلاحية، أو تذكرة دعم. لا نرسل رسائل تلقائية بلا limits وconsent وقواعد منع الإزعاج.

## الشارات

تكون الشارات مرتبطة بسلوك تعليمي حقيقي مثل أول أسبوع منتظم، إكمال وحدة، تحسن في موضوع، أو حل عدد معين من الأسئلة. لا نعتمد على leaderboard قاسٍ؛ نركز على التحسن الشخصي، ويمكن إخفاء الشارات حسب إعدادات المنصة.

## مخرجات القبول

يستطيع الطالب معرفة ما يفعله الآن، ويستطيع المشرف استخراج الطلاب المتوقفين مع سبب قابل للتصرف. لا يحصل الطالب على Badge نتيجة فتح الشاشة فقط؛ كل Badge لها rule قابلة للتدقيق.

# المرحلة 9: مركز القرارات والتحليلات التشغيلية

## الهدف

تحويل البيانات الموجودة إلى قرارات يومية قابلة للتنفيذ، بدل أرقام زيارات عامة.

## لوحات الإدارة

يشمل المركز funnel من المشاهدة إلى شراء، إكمال الكورس، متوسط وقت المشاهدة، drop-off لكل درس، أداء الامتحانات والموضوعات، الطلاب المتوقفين، الطلبات العالقة، jobs الفيديو، وصحة التكاملات. كل مؤشر يجب أن يملك تعريفًا زمنيًا ومصدر بيانات واضحًا.

نضيف Decision Cards مثل: «12 طالبًا توقفوا عند الدرس نفسه»، «3 فيديوهات بها فشل متكرر»، «كورس يحقق مبيعات عالية وإكمالًا منخفضًا»، أو «امتحان به سؤال يخطئ فيه معظم الطلاب». كل بطاقة تقود إلى إجراء: فتح Content QA، إنشاء مراجعة، إرسال رسالة، أو تعديل Release.

## مخرجات القبول

تتطابق الأرقام مع استعلامات مرجعية معتمدة، وتُحترم timezone والفترة الزمنية، ولا تعرض اللوحات بيانات شخصية لمستخدم غير مخول. أي metric جديد له تعريف موثق واختبار sanity check.

# المرحلة 10: تقوية المساعدين والفيديو والاتصالات

## صلاحيات المساعدين

نقسم الصلاحيات إلى domain/action مثل `students.view` و`students.manage` و`payments.view` و`orders.approve` و`content.manage` و`exams.manage` و`security.manage`. نضيف role templates، وإمكانية تخصيص محدود، وتسجيل كل عملية حساسة. لا نستخدم اسم route كبديل عن permission.

## Video Operations Center

نعرض jobs بحالات queued وprocessing وfailed وready، ووقت الانتظار، مدة المعالجة، حجم الملف، الدرس، الفيديو، retry count، وزر retry آمن. نضيف worker heartbeat وstale-job detector وdead-letter أو failed queue. يجب إخفاء raw error الحساس عن المستخدم العادي مع رسالة مفهومة، وحفظ التشخيص للموظف المخول.

## WhatsApp

نجعل الإرسال idempotent، ونمنع تكرار رسالة الموافقة، وندعم retry محدودًا مع backoff، ونحفظ provider message ID والحالة. نضيف opt-out، قوالب معتمدة، وaudit للرسائل التشغيلية.

# المرحلة 11: الاختبارات والهجرة والإطلاق

## استراتيجية الاختبارات

نحتاج اختبارات unit لمنطق Entitlement وmastery وbadge rules، واختبارات integration للطلبات والاشتراكات والفيديو، واختبارات authorization/RLS لكل role، واختبارات E2E للمسارات: تسجيل، شراء، فتح محتوى، مشاهدة، تقدم، امتحان، دعم، وإلغاء جهاز.

قبل production، ننشئ نسخة staging من schema وبيانات صناعية، وننفذ migration على نسخة استرجاعية، ثم نتحقق من counts والعلاقات والـ indexes. أي migration يجب أن تكون backward-compatible إذا كان هناك rolling deploy.

## الإطلاق التدريجي

يتم إطلاق كل وحدة خلف feature flag. يبدأ التفعيل على admin واحد أو مدرس تجريبي، ثم مجموعة صغيرة من الطلاب، ثم بقية المنصة. نراقب error rate، auth failures، video failures، order duplication، latency، وsupport tickets. لكل migration خطة rollback مكتوبة.

## Definition of Done

لا تعتبر المرحلة منتهية إلا إذا كان الكود مراجعًا، migration مجربًا على staging، الصلاحيات مختبرة، logs وaudit موجودة، واجهة الخطأ مفهومة، وثيقة التشغيل محدثة، ومعايير القبول محققة من مستخدم إداري وطالب تجريبي.

# 5. ترتيب التنفيذ العملي لأول 30 يومًا

| الأسبوع | التنفيذ |
|---|---|
| 1 | إصلاح database wiring والـ proxy، تثبيت staging، backup/restore test، وhealth checks. |
| 2 | اعتماد domain model، Entitlement contract، role matrix، وقرار sales mode الاختياري. |
| 3 | تنفيذ Order State Machine وorder events وidempotency، ثم ربط الصلاحيات الحالية بالخدمة الموحدة. |
| 4 | بدء Student 360، وإضافة Content QA الأساسي، مع Video Operations snapshot للـ jobs الحالية. |

بعد أول 30 يومًا يجب أن تصبح المنصة مستقرة تشغيليًا، ويكون لدينا أساس موحد للصلاحيات، ونسخة أولى من أدوات الإدارة التي تعالج المشاكل اليومية بدل تأجيلها.

# 6. ترتيب الأولوية إذا اضطررنا للاختصار

إذا كان الوقت أو الفريق محدودًا، يكون الترتيب الإجباري هو: **إصلاح الإنتاج، Entitlement Service، Student 360، Content QA، Video Operations، Order State Machine، Exam Attempts، Mastery Map، Exam Review، ثم Release وBundles وباقي التحسينات**. لا أنصح ببدء AI Tutor أو شارات متقدمة قبل تثبيت البيانات والصلاحيات والتقييم.

# 7. قرارات يجب حسمها قبل البرمجة

| القرار | الاختيار المقترح |
|---|---|
| نطاق الاشتراك | لكل منتج/محتوى أو مدرس، وليس feature إجبارية على كل المنصة. |
| الوصول بعد انتهاء الاشتراك | يحدد لكل plan: منع فوري، grace period، أو استمرار progress مع منع المحتوى الجديد. |
| التقييم | attempts مستقلة، مع snapshot للأسئلة والنسخ. |
| Release | جدولة حسب التاريخ، وفتح اختياري حسب prerequisite أو مدة الاشتراك. |
| mastery | قواعد deterministic أولًا، ثم تطويرها بعد توفر بيانات كافية. |
| رسائل الإنقاذ | opt-in، limits، وقوالب قابلة للتعديل، لا إرسال عشوائي. |
| البيانات الشخصية | أقل صلاحية لازمة، وStudent 360 حسب role مع audit. |
| الربط مع RLS | اختبار فعالية RLS مع طريقة Prisma الحالية، وعدم افتراض أنها تعمل تلقائيًا مع كل اتصال. |

# 8. الخلاصة

الخطة لا تبدأ بإعادة كتابة المنصة؛ تبدأ بتثبيت ما هو موجود، ثم وضع مصدر واحد للصلاحيات، ثم بناء أدوات الإدارة والمحتوى، ثم التقييم والإتقان، ثم التجربة الذكية والتحليلات. بهذا الترتيب تظل المبيعات والمحتوى الحاليان يعملان، وتصبح كل Feature جديدة قابلة للقياس والرجوع عنها.

أكبر قيمة متوقعة تأتي من ثلاثة محاور مترابطة: **Entitlement Service موحدة، Content/Release Workflow مضبوط، وخريطة إتقان مرتبطة بالامتحانات**. أما الاشتراكات والـ Bundles فتدخل كطبقة تجارية اختيارية فوق هذا الأساس، دون إجبار أي مدرس على تغيير طريقة البيع الحالية.
