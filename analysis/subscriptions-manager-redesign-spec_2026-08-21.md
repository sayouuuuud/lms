# مواصفات إعادة بناء إدارة الاشتراكات

## 1. القرار التجاري غير القابل للكسر

الاشتراك **طبقة وصول إضافية** وليس بديلًا عن الشراء الفردي. يمكن للمدرس تشغيل أحد الأوضاع التالية من إعدادات المنصة:

| الوضع | الوصول المكتسب من الطلبات المعتمدة | الوصول المكتسب من الاشتراك |
|---|---|---|
| `purchases_only` | يعمل | متوقف تمامًا |
| `subscriptions_only` | يظل محفوظًا وفعّالًا إذا كان المدرس اختار تعطيل البيع الفردي | يعمل فقط عبر اشتراك صالح |
| `hybrid` | يعمل دائمًا | يضاف إلى الوصول المملوك ما دام الاشتراك صالحًا |

عند انتهاء الاشتراك أو إيقافه، يفقد الطالب **الوصول الممنوح بالاشتراك فقط**. لا تُحذف الطلبات ولا يتأثر أي كورس أو درس اشتراه الطالب مسبقًا. لذلك يجب أن تكون النتيجة النهائية دائمًا اتحاد مجموعتين مستقلتين:

`الوصول النهائي = الوصول المملوك بالشراء ∪ الوصول الممنوح بالاشتراك`

ولا يجوز أن يختار الكود أحد المصدرين ويستبعد الآخر.

## 2. قواعد الوصول

يُعتبر الطلب مالكًا للمحتوى فقط إذا كان `orders.status = approved`. ويستمر هذا الوصول حتى لو أصبح اشتراك الطالب منتهيًا أو ملغى أو موقوفًا، وفق سياسة الشراء الحالية.

يُعتبر الاشتراك مؤثرًا في الوصول عندما يكون وضع المنصة يسمح بالاشتراكات، وحالة الاشتراك `active`، ويقع الوقت الحالي داخل `start_date` و`end_date`. إذا استُخدمت فترة سماح، يجب أن تكون حالة صريحة `grace` مع `grace_until` واضح، وألا تتحول نهاية الاشتراك المنتهية إلى وصول دائم بالخطأ. انتهاء فترة السماح يحول الاشتراك إلى `expired` ولا يمنح أي وصول اشتراكي.

نطاق الخطة مستقل عن مدتها. النطاقات المدعومة هي:

| نوع النطاق | المعنى |
|---|---|
| `all_released` | كل المحتوى المنشور والمتاح في وقت التحقق |
| `branch` | كل المحتوى المنشور في فرع محدد |
| `stage` | كل المحتوى المنشور في مرحلة محددة |
| `term` | كل الكورسات التابعة لترم محدد ثم محاضراتها ودروسها |
| `course` | كورس محدد ثم محاضراته ودروسه |
| `lecture` | محاضرة محددة ودروسها |

كل استعلام محتوى يجب أن يطبق `is_published` و`release_date`، فلا يمنح الاشتراك وصولًا إلى محتوى غير منشور أو لم يحن موعده.

## 3. نموذج البيانات المقترح

يجب الحفاظ على الجداول الحالية وترقية البيانات دون حذف سجلات الاشتراك القديمة. الإضافات المقترحة هي:

### 3.1 `subscription_plans`

تظل الحقول الحالية (`title`, `description`, `price`, `duration_days`, `is_active`, `stage_id`, `branch_id`) متوافقة، وتضاف حقول حوكمة مثل:

- `code` اختياري فريد بعد تنظيف البيانات.
- `billing_period` بقيم `month`, `term`, `year`, `custom` للاستخدام في العرض والتحليل.
- `scope_mode` بقيمة `all_released` أو `selected`.
- `allow_manual_assignment`.
- `created_by`, `updated_by`.
- `archived_at` عند الإيقاف الإداري النهائي.

وللتوسع الصحيح تُضاف `subscription_plan_scopes` بدل حشر النطاقات في أعمدة متعددة:

- `id`, `plan_id`, `scope_type`, `scope_id`, `created_at`.
- قيد فريد على `(plan_id, scope_type, scope_id)`.
- `scope_id` يكون nullable فقط عندما يكون النوع `all_released`.
- لا يسمح التطبيق بنطاق فارغ في خطة `selected`.

تُستخدم `stage_id` و`branch_id` القديمة كـfallback للتوافق مع الخطط الحالية، ثم تُنسخ إلى جدول النطاقات في migration على staging قبل اعتماد المسار الجديد.

### 3.2 `student_subscriptions`

تضاف حقول دورة الحياة ومصدر المنح والدفع والتدقيق:

- `status`: `active`, `grace`, `expired`, `cancelled`, `suspended`.
- `source`: `manual`, `order`, `import`, `system`.
- `payment_status`: `unpaid`, `pending`, `paid`, `refunded`, `waived`.
- `payment_reference`.
- `grace_until`.
- `cancelled_at`, `cancel_reason`.
- `suspended_at`, `suspend_reason`.
- `assigned_by`, `updated_by`.
- `last_payment_at`, `next_billing_at`، مع اعتبار التجديد التلقائي غير مدعوم حتى يوجد provider موثوق.
- `plan_snapshot` بصيغة JSON لحفظ عنوان الخطة وسعرها ونطاقها وقت المنح.

يُمنع إنشاء اشتراك متداخل لنفس الطالب على نفس النطاق بطريقة صامتة. يجب أن يقرر النظام صراحة: رفض التداخل، أو تمديد الاشتراك القائم، أو إنشاء اشتراك منفصل بعد تحذير ومبرر محفوظ.

### 3.3 `subscription_events`

سجل append-only لكل عملية حساسة، ويشمل:

- `subscription_id`, `event_type`, `actor_user_id`, `from_status`, `to_status`.
- `reason`, `payment_reference`, `metadata`, `created_at`.

الأحداث الأساسية: `created`, `activated`, `extended`, `grace_started`, `renewed`, `cancelled`, `suspended`, `reactivated`, `expired`, `refunded`, `scope_changed`.

## 4. خدمة القرار الموحدة

يجب إنشاء خدمة واحدة مثل `getStudentEntitlements` أو `getEntitledContent`، وتصبح المصدر الوحيد لصفحات الطالب وواجهات التحقق. الخدمة:

1. تقرأ الطلبات المعتمدة دائمًا.
2. تقرأ الاشتراكات الصالحة فقط إذا كان وضع المنصة يسمح بها.
3. تحل نطاقات الخطط إلى course IDs وlecture IDs.
4. تدمج النتائج في `Set` لمنع التكرار.
5. تطبق release/publish filters.
6. تعيد مصدر كل entitlement عند الحاجة للتدقيق: `purchase` أو `subscription` أو `both`.

يجب إبقاء أسماء الدوال القديمة كـwrappers مؤقتة حتى لا تنكسر الصفحات الحالية، لكن لا يجوز أن تحتوي wrappers على منطق بديل مختلف.

## 5. تصميم صفحة Subscriptions Manager

تُعاد الصفحة إلى مركز تشغيل لا إلى جدول خطط بسيط. تكون عربية بالكامل وتحتوي على:

### لوحة الملخص

تعرض الفترة المختارة والمنطقة الزمنية ومؤشر حالة الاشتراكات، مع المقاييس التي يمكن حسابها من البيانات الحالية فقط:

- وضع الاشتراكات الحالي: شراء فقط، اشتراكات فقط، أو مختلط.
- عدد الخطط النشطة والمؤرشفة.
- عدد الاشتراكات النشطة.
- عدد الاشتراكات داخل grace.
- عدد المنتهية خلال الفترة.
- عدد الطلاب المشتركين الفريدين.
- قيمة الاشتراكات الممنوحة أو المدفوعة خلال الفترة، مع تسمية دقيقة تمنع تسميتها MRR إذا لم توجد فوترة متكررة مؤكدة.
- نسبة الاحتفاظ المحسوبة من اشتراكات لها تاريخ بداية ونهاية صالحين.

كل بطاقة يجب أن تعرض تعريف المقياس، مصدره، الفترة، وحالة sanity؛ والبيانات الفارغة تظهر صفرًا أو `لا توجد بيانات` بدل `NaN`.

### تبويب إعداد سياسة الوصول

يعرض الوضع الحالي ويشرح بالعربية أثر كل وضع على المشتريات والاشتراكات. تغيير الوضع يحتاج صلاحية `manage`، وتأكيدًا صريحًا، وسجل تدقيق يوضح القيمة القديمة والجديدة. لا يؤدي تعطيل الاشتراكات إلى حذف الخطط أو الاشتراكات التاريخية.

### تبويب الخطط

يدعم إنشاء وتعديل وأرشفة الخطط، وتحديد مدة الخطة ووحدتها، والسعر، والنطاق، والمحتوى المشمول. قبل الحفظ يعرض ملخصًا قابلًا للفهم: عدد الكورسات والمحاضرات المتوقع فتحها، وما إذا كان النطاق كل المحتوى أو محتوى محدد. إيقاف الخطة يمنع المنح الجديدة فقط ولا يلغي تلقائيًا اشتراكات قائمة.

### تبويب الطلاب والاشتراكات

يدعم البحث بالاسم والبريد والهاتف، والفلاتر حسب الخطة والحالة والنطاق وتاريخ الانتهاء ومصدر الاشتراك. صف الطالب يعرض:

- الاشتراك الحالي وحالته.
- تاريخ البداية والنهاية وgrace إن وجدت.
- ما يملكه بالشراء الفردي.
- ما يضاف له بالاشتراك.
- إجمالي الوصول النهائي.
- آخر حدث تدقيقي.

الأفعال الحساسة هي منح، تمديد، بدء grace، إيقاف، إلغاء، إعادة تفعيل، وتسجيل دفعة. كل فعل يحتاج سببًا اختياريًا/إلزاميًا حسب نوعه، ويكتب event ذريًا مع التغيير.

### تبويب سجل التدقيق

يعرض الأحداث append-only مع actor ووقت العملية والحالة القديمة والجديدة والسبب والمرجع المالي، دون عرض أسرار provider أو بيانات دفع حساسة غير لازمة.

## 6. الصلاحيات والحوكمة

تُضاف ResourceKey مستقل باسم `subscriptions` بدل استخدام `settings` بشكل فضفاض. القراءة تعرض البيانات دون أفعال تغيير، بينما `manage` مطلوب لتغيير الوضع والخطط والاشتراكات. الأدمن يملك كل الصلاحيات، والمساعد لا يرى إلا ما منحه له `assistant_permissions`.

كل Server Action يعيد التحقق من الصلاحية داخل الخادم، ولا يعتمد على إخفاء الزر في الواجهة. يجب التحقق من صحة UUIDs والحالات والتواريخ، ومنع تمديد اشتراك منتهي دون فعل reactivation واضح، ومنع تعديل plan snapshot التاريخي.

## 7. خطة migration الآمنة

1. أخذ backup قابل للاسترجاع من staging ثم قراءة schema الفعلي.
2. إضافة الجداول والحقول الجديدة nullable/defaulted حتى لا تتأثر السجلات القائمة.
3. نقل `stage_id` و`branch_id` القديمة إلى `subscription_plan_scopes` دون حذف الأصل.
4. إضافة الفهارس والقيود بعد فحص التكرارات والتداخلات الموجودة.
5. تشغيل backfill للـsnapshot وsource على السجلات القديمة بقيم `legacy` أو `manual` الموثقة.
6. اختبار read/write على staging.
7. اختبار اتحاد purchase + subscription بحالات الطالب الأربع: شراء فقط، اشتراك فقط، الاثنان، ولا شيء.
8. أخذ backup جديد من `upgrade`، ثم تطبيق نفس SQL فقط بعد نجاح staging.
9. التحقق من counts والقيود والعلاقات، ثم تشغيل smoke tests.

لا يُنفذ أي `DROP`, `TRUNCATE` أو حذف لسجلات الطلبات/الاشتراكات القائمة.

## 8. معايير القبول

يُعتبر التغيير مقبولًا فقط إذا نجحت جميع الحالات التالية:

| الحالة | النتيجة المطلوبة |
|---|---|
| طالب اشترى كورسًا فقط | يصل إلى الكورس حتى دون اشتراك |
| طالب لديه اشتراك فقط | يصل فقط إلى نطاق الخطة المنشور |
| طالب لديه شراء واشتراك | يحصل على اتحاد المصدرين |
| انتهاء الاشتراك | يختفي الوصول الاشتراكي وتظل المشتريات |
| اشتراك فرع/ترم/كورس | لا يصل الطالب إلى محتوى خارج النطاق |
| خطة موقوفة | تمنع المنح الجديدة ولا تحذف القائمة |
| إلغاء اشتراك | يسجل event ولا يحذف التاريخ |
| duplicate assignment | رفض أو تمديد صريح، لا صفوف متداخلة صامتة |
| تغيير وضع المنصة | يطبق على الاشتراكات فقط ويحافظ على المشتريات |
| مساعد بلا صلاحية manage | يمكنه القراءة فقط أو يُرفض حسب policy |
| بيانات فارغة | لا قيم `NaN` ولا crash ولا كشف أخطاء خام |

## 9. حدود التنفيذ الحالية

النسخة الحالية لا تحقق هذه المواصفات بالكامل. أبرز العيوب المثبتة هي أن `hasActiveSubscription` يقرر وصولًا عامًا، وأن `getPurchasedLectureIds` و`getPurchasedCourseIds` يستبدلان مسار المشتريات عند وجود اشتراك بدل دمجهما، وأن صفحة الإدارة لا تحتوي على خطة/نطاق/سجل/إحصائيات تشغيلية كافية، وأن نموذج البيانات لا يحتوي على scopes أو lifecycle events أو payment/audit metadata. لذلك يجب تنفيذ إصلاح الخدمة والـschema قبل اعتبار إعادة تصميم الصفحة مكتملة.

هذا المستند هو مرجع التنفيذ والقبول لهذه المهمة، وليس إعلانًا بأن أي migration جديدة طُبقت على الإنتاج.
